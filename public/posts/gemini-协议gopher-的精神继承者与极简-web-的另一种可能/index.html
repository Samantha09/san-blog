Gemini 协议：Gopher 的精神继承者与极简 Web 的另一种可能

Jun 9, 2026 分钟阅读

一、Gemini 是什么

Gemini 是一种新兴的互联网应用层协议，诞生于 2019 年，由 Solderpunk 发起设计。它的定位非常明确：

介于 Gopher 和 HTTP 之间，比 Gopher 更现代，比 HTTP 更简单。

如果你厌倦了现代 Web 的臃肿——动辄几 MB 的 JavaScript、无穷无尽的 Cookie 弹窗、追踪脚本和广告框架——Gemini 提供了一条回归信息本质的逃生通道。

二、为什么需要 Gemini

2.1 Gopher 太古老

Gopher（1991）的设计理念很棒（极简、层级、纯文本），但它有硬伤：

  • 无加密：明文传输，在现代互联网不可接受
  • 无错误码：成功失败靠约定，调试困难
  • 无类型系统：资源类型靠单个字符标识，扩展性差
  • 无输入机制：除了搜索框，几乎无法与用户交互

2.2 HTTP 太复杂

HTTP/1.1 → HTTP/2 → HTTP/3，每一次迭代都在增加复杂度：

特性 HTTP 现状
Header 数十个标准头，无限自定义头
方法 GET/POST/PUT/PATCH/DELETE/OPTIONS…
状态码 40+ 个，还要细分
扩展 Cookie、CORS、HSTS、CSP、SRI…
渲染引擎 HTML + CSS + JS，永恒的安全噩梦

Gemini 的设计哲学是有意识地做减法：

“不是 HTTP 做不了的我们不加，而是 Gopher 没做好的我们才补。”

三、Gemini 的核心设计

3.1 协议栈极简

+------------+
| Gemini     |  ← 应用层协议（类似 HTTP）
+------------+
| TLS 1.2+   |  ← 强制加密（类似 HTTPS）
+------------+
| TCP        |  ← 传输层
+------------+

Gemini 强制 TLS，没有明文传输的选项。这避免了 HTTP 历史上 “HTTP 默认、HTTPS 可选” 的安全债。

3.2 请求格式

一个 Gemini 请求就是一个 URI + CRLF：

gemini://example.com/document.gmi\r\n

没有 Header。没有方法。没有 Cookie。

对比 HTTP：

GET /document HTTP/1.1
Host: example.com
User-Agent: Mozilla/5.0
Accept: text/html
Accept-Language: zh-CN
Accept-Encoding: gzip
Connection: keep-alive
Cookie: session=abc123

Gemini 的请求永远只有一行。

3.3 响应格式

<STATUS> <META>\r\n<BODY>
  • STATUS：两位数字状态码（比 HTTP 少得多）
  • META：人类可读的状态说明或 MIME 类型
  • BODY：二进制内容，直接跟随

例子：

20 text/gemini\r\n# Hello, Gemini!\r\nThis is a simple document.

3.4 状态码极简

状态码 含义 对比 HTTP
20 成功 200
30 重定向 301/302
40 临时失败 404/500
50 永久失败 410
60 需要客户端证书 无直接对应

没有 201、204、206、301、302、304、400、401、403、404、405、500、502、503… 的细分。Gemini 认为：客户端不需要知道这么多细节。

3.5 输入机制：原生支持

Gopher 几乎没有输入能力。Gemini 引入了 INPUT 状态码 (10)：

10 What is your name?\r\n

客户端收到 10 后，弹出一个输入框，用户提交后客户端再发送一次请求：

gemini://example.com/search?name=Alice\r\n

没有 POST body，没有表单编码。输入通过 Query String 传递，极简但够用。

四、Gemini 文本格式（text/gemini）

Gemini 不传输 HTML。它有自己的标记语言，比 Markdown 更严格，比 HTML 更简单。

4.1 语法一览

## 二级标题
### 三级标题

普通文本段落，自动换行。

* 列表项 1
* 列表项 2
* 列表项 3

> 引用文本

```代码块
自动识别，无需指定语言

**注意**：
- 没有内联样式（粗体、斜体、下划线）
- 没有图片内嵌（图片作为独立链接）
- 没有表格
- 没有超链接文本混排（链接独占一行）

### 4.2 设计理念

> "内容创作者应该专注于**写什么**，而不是**怎么渲染**。**"

Gemini 客户端决定如何渲染 `text/gemini`，作者无法干预。这彻底消除了：
- CSS 漏洞和注入
- 视觉欺骗钓鱼（"这个按钮看起来安全"）
- 跟踪像素和字体指纹

## 五、Gemini vs Gopher vs HTTP

| 特性 | Gopher | Gemini | HTTP |
|------|--------|--------|------|
| 诞生时间 | 1991 | 2019 | 1991 |
| 传输加密 | ❌ 无 | ✅ 强制 TLS | ⚠️ 可选 (HTTP/3 强制) |
| 请求复杂度 | 极简 | 极简 | 复杂 |
| 响应头 | 无 | 极简一行 | 复杂多行 |
| 内容格式 | 文本/二进制 | text/gemini + 任意 | HTML/CSS/JS/任意 |
| 交互能力 | 搜索框 | 输入框 (10) | 表单/JS/AJAX/WebSocket |
| 状态码 | 无 | 5 个 | 40+ 个 |
| 扩展性 | 差 | 故意限制 | 极强 |
| 客户端实现 | 容易 | 非常容易 | 极其困难 |
| 现代生态 | 复古社区 | 活跃增长 | 统治互联网 |

## 七、Gemini 的局限性与批评

### 7.1 功能过于受限

- 无法上传文件（无 POST body）
- 无法构建复杂应用（无脚本、无状态管理）
- 内联链接缺失影响某些文档类型（学术论文、百科）

### 7.2 生态隔离

Gemini 空间（称为 "Smol Web" 或 "Capsule"）与主流互联网几乎不互通。你不可能在 Gemini 上阅读一篇包含交互式图表的数据新闻。

### 7.3 客户端证书的设计争议

状态码 `60` 要求客户端 TLS 证书用于身份认证，但证书管理对普通用户来说门槛过高，实际使用率低。

---

## 八、适用场景总结

| 场景 | 是否适合 Gemini | 原因 |
|------|----------------|------|
| 个人博客/日记 | ✅ 完美 | 纯文本，无广告，隐私优先 |
| 技术文档/手册 | ✅ 适合 | 结构化内容，无需交互 |
| 新闻/资讯站点 | ⚠️ 可以 | 缺乏图片内嵌和富媒体 |
| 电商/支付 | ❌ 不适合 | 无状态管理、无安全输入机制 |
| 社交网络 | ❌ 不适合 | 无实时推送、无评论系统 |
| 内部知识库 | ✅ 适合 | 低维护成本、无安全风险 |
| 嵌入式/IoT | ✅ 适合 | 协议极简、TLS 内置 |

---

## 九、总结

Gemini 不是来取代 HTTP 的。它是一个**有意的替代方案**，为那些：

- 厌恶 Web 复杂化的开发者
- 关心隐私和去跟踪的普通用户
- 资源受限环境下的系统设计者

提供了一条退路。

如果你也对极简协议感兴趣，可以从安装 **Lagrange** 或 **Amfora** 开始，访问 `gemini.circumlunar.space`（Gemini 项目主页），体验一下这个"轻 100 倍的 Web"。
